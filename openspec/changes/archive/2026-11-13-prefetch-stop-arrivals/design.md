## Context

В текущем WatchBus PebbleKit JS загружает прогноз и расписание для выбранного UUID. Прогноз требует одного запроса `stop_v2`, а расписание может требовать нескольких запросов по маршрутам и направлениям. Список площадок строится локально.

## Goals / Non-Goals

**Goals**

- Показать список независимо от скорости источников и использовать загруженные прогнозы при открытии табло.
- Загружать прогнозы по мере просмотра списка и ограничить одновременные фоновые запросы.

**Non-Goals**

- Периодическое обновление всех площадок списка и загрузка полного расписания для всех площадок.

## Decisions

1. Разделить получение прогноза и расписания, сохранив общую нормализацию и правила сопоставления рейсов. Кэшировать прогноз и плановые строки отдельно по UUID. Для прогноза использовать текущий срок действия до двух минут. Проверять время прибытия при формировании каждого экрана.
2. Ставить первые пять UUID в очередь сразу после поиска. Часы сообщают о новых видимых и выделенной площадках. В фоне одновременно выполняются до двух запросов прогноза. Повторные запросы одной площадки объединяются. Новая выдача отменяет задания старого списка, которые ещё не запущены.
3. Загружать расписание для выделенной площадки после паузы 750 мс, если прогноз успешно завершился и действующих строк нет. Одновременно выполнять одну фоновую загрузку расписания. При Select выбранная площадка получает отдельный приоритет перед очередью. Уже выполняющиеся запросы для неё используются повторно. Пока табло открыто, новые фоновые задания списка ждут.
4. Передавать краткие данные с UUID площадки или с идентификатором выдачи и индексом, однозначно привязанным к UUID. Хранить компактные данные о двух прибытиях с абсолютным временем, типом и сроком действия. Высоту строки выбирать с учётом существующих названия, расстояния и подсказки направления. Обновления отдельных строк сохраняют выделение.
5. Отображать кэшированные прогнозы сразу при открытии табло. Добавлять расписание после завершения загрузки и сохранять существующие правила обработки ошибок, таймеров и HTTP 429.

## Risks / Trade-offs

- Фоновое расписание может занять несколько запросов → запускаем его только после паузы на выделенной площадке и отдаём приоритет открытому табло.
- Ответ может прийти после смены списка или экрана → проверяем идентификатор площадки и актуальность перед показом.
- Дополнительные строки снижают число видимых площадок → краткое табло ограничено двумя прибытиями.

## Приёмка

Пользователь подтвердил, что изменение можно архивировать. Отдельный результат проверки мгновенного открытия кэшированного табло на физической связке не зафиксирован. Сценарий проверен в эмуляторе.
